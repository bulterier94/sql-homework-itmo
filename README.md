# Выбор СУБД и обоснование

## 1. Описание проекта

Система предназначена для управления коворкингом: хранения информации о клиентах и помещениях, а также создания и отмены бронирований рабочих мест и помещений. Основные операции - регистрация пользователя, просмотр доступных помещений, создание бронирования и изменение его статуса.

Анализ требований находится в [`docs/requirements.md`](docs/requirements.md).

## 2. Выбор СУБД

Для проекта выбрана **PostgreSQL 16**.

|---|---|---|---|

| Ограничения целостности | PK, FK, UNIQUE, CHECK, exclusion constraints | PK, FK, UNIQUE, CHECK (в актуальных версиях), ограничения InnoDB | PK, FK, UNIQUE, CHECK |
| Безопасность и RLS | Роли, права, Row-Level Security (RLS) на уровне строк | Роли и права; встроенный аналог PostgreSQL RLS отсутствует | Роли, права, Row-Level Security |
| Экосистема и диагностика | `EXPLAIN`, `EXPLAIN ANALYZE`, `pg_stat_statements`, большое число расширений | `EXPLAIN`, Performance Schema, инструменты мониторинга | Actual Execution Plan, Query Store, развитые средства администрирования |

### Вывод

PostgreSQL подходит проекту, потому что данные имеют чёткие связи: пользователь создаёт бронирования, а каждое бронирование относится к определённому помещению. Внешние ключи и проверки `CHECK` позволяют обеспечить целостность данных на стороне БД. Особенно полезно ограничение `EXCLUDE` совместно с расширением `btree_gist`. Оно запрещает пересекающиеся активные бронирования одного помещения. PostgreSQL также поддерживает транзакции, индексы и RLS, поэтому подходит как для повседневных операций, так и для последующей аналитики.

## 3. SQL vs NoSQL

### Сценарий: хранение бронирований коворкинга

Система должна создавать бронирования, показывать бронирования пользователя за период, находить занятость конкретного помещения и формировать отчёт по загрузке помещений.

**PostgreSQL:**
- Таблицы `app_user`, `room`, `booking`.
- `booking` содержит внешние ключи на пользователя и помещение.
- Для списка бронирований пользователя нужен JOIN с помещением, если требуется вывести его название/код.
- Создание бронирования и связанные изменения выполняются транзакционно.
- Ограничения FK, CHECK и EXCLUDE защищают данные от ссылок на несуществующие записи, некорректных интервалов и пересечения активных броней.

**MongoDB:**
- Коллекция `users` хранит документы пользователей.
- Коллекция `rooms` хранит документы помещений.
- Коллекция `bookings` хранит бронирование, а сведения о помещении и пользователе могут дублироваться внутри документа либо храниться как идентификаторы.
- При дублировании данных для чтения JOIN обычно не нужен, но обновление названия помещения потребует обновить копии в документах. При хранении только идентификаторов понадобятся дополнительные запросы.
- Для согласованного изменения нескольких документов может потребоваться транзакция; проверку отсутствия пересечений бронирований придётся отдельно проектировать на уровне приложения/транзакций и индексов.

**Вывод:** для основного сценария выбирается SQL-модель PostgreSQL. В проекте важны связи между пользователями, помещениями и бронированиями, а также строгая целостность и запрет двойного бронирования. Документная модель удобна для самостоятельных документов с часто меняющейся структурой, но здесь её гибкость не перевешивает преимущества реляционных связей и ограничений.

## 6. ДЗ, выбор первичных ключей

В проекте системы управления коворкингом для первичных ключей таблиц `app_user`, `room` и `booking` выбраны суррогатные идентификаторы (`user_id`, `room_id`, `booking_id`). При этом `email` пользователя и `code` помещения остаются естественными уникальными атрибутами и защищаются ограничением `UNIQUE`.

### Аргументы за суррогатный ключ

1. **Стабильность идентификатора.** Email может измениться, например при смене почтового адреса клиента. Код помещения также может быть изменён при перенумерации. Если использовать эти значения как первичные ключи, изменение потребует обновлять внешние ключи во всех связанных записях. Суррогатный `user_id` или `room_id` останется прежним.
2. **Компактные и простые связи.** Числовые идентификаторы имеют небольшой фиксированный размер и удобны для внешних ключей и JOIN. Для бронирования достаточно хранить `user_id` и `room_id`, а не копировать длинные текстовые значения.

### Аргументы за естественный ключ

1. **Смысловая ценность.** Естественный ключ уже существует в предметной области и имеет значение для пользователя. Например, email идентифицирует учётную запись при входе, а код помещения позволяет сотруднику найти конкретную комнату. Отдельный идентификатор не заменяет необходимость уникальности этих значений.
2. **Отсутствие дополнительного атрибута.** Если значение действительно уникально, обязательно, неизменно и не содержит конфиденциальных данных, его можно использовать как первичный ключ. Это уменьшает число столбцов и позволяет напрямую видеть идентификатор объекта в данных.

### Вывод

Для `app_user`, `room` и `booking` оставим суррогатные первичные ключи. Email и код помещения сохраняем как `UNIQUE` атрибуты, что не позволяет создавать дубликаты, но не делает связи зависимыми от значений, которые могут измениться. Для бронирования естественный ключ подобрать неудобно, комбинация пользователя, помещения и времени не гарантирует простой и неизменный идентификатор записи. Поэтому отдельный `booking_id` - наиболее практичный вариант.
